### 摘要（可直接填入报名表单的"一页项目说明"）

moonnet-lab 是一个用 MoonBit 实现的确定性数据包级网络仿真与 TCP 拥塞控制实验平台。它把网络行为建模成纯函数：给定场景文件与随机种子，任意多次运行都产出逐字节一致的事件序列与指标，因此算法对比、参数扫描与结论回归都能像代码一样被复现和版本化。已完成确定性事件内核、链路与队列模型（drop-tail / RED / CoDel 三种队列管理策略）、完整 TCP 状态机（RFC 6298 的 RTO 估计、Karn 算法、快速重传与多丢包恢复）、可插拔拥塞控制接口与 Reno、CUBIC，以及"实验即数据"的场景文件、对比、扫描与多流公平性。95 个测试全部通过，CI 持续验证。开发中它两次推翻过自己的结论，也留下一个尚未解释的异常，都记在路线图里。仓库：https://github.com/Ljh684/moonnet-lab

## 一、项目目标与应用场景

**要解决的问题**：调拥塞控制、判断缓冲区该多大、评估链路丢包时该选哪个算法——答案通常来自真实设备上的试错，或一次无法复现的临时脚本，换一台机器、换一次运行数字就变了，于是结论既无法比较也无法积累。

**做法**：把网络行为建模成纯函数，给定拓扑、流量、参数与随机种子，输出确定的事件序列与指标；算法对比、实验回溯、结论回归因此同时成立。

**应用场景**：网络工程师改参数或切算法之前先在仿真里做 A/B 对比；拥塞控制教学（每条结论对应一条可重跑的命令）；MoonBit 生态（为将来的网络栈提供可复现的行为验证台）；AI 代理（确定性加机器可读报告，可以反复迭代实验而不是靠猜）。

## 三、技术路线说明

- **分层严格**：`src/sim` 不认识网络，`src/net` 不认识 TCP，`src/tcp` 不认识文件；库只接受字符串，把文件变成字符串是命令行工具的事。
- **确定性的三个支柱**：时间是 `Int64` 皮秒；事件按 `(时间, 调度序号)` 排序；随机数自带且在测试里钉死参考向量。三者都不是承诺，而是会被断言抓住的约束。
- **机制与策略分离**：连接负责序号、定时器、重传与流量控制；`CongestionControl` 只回答"现在允许多少字节在途"以及六个事件发生时窗口怎么变。换一个算法不需要改一行机制代码。
- **实验即数据**：场景文件 → 运行 → 固定字段顺序的 JSON。`--seeds N` 报告均值与最快/最慢，因为丢包场景下总时间由少数几次 60 秒封顶的超时主导，一次运行不是一个测量。
- **AI 工具的作用**：模块实现、测试与文档草稿由 AI 承担；算法保真度、实验设计、以及判断哪些数字不可信由人把关。三个具体例子写在设计文档里。结论：AI 让实现速度提升一个数量级，但实验的可信度不能外包。

## 四、风险分析与应对方案

| 风险 | 应对 |
| --- | --- |
| 保真度受质疑（仿真不等于真实 TCP） | 算法逐条对照 RFC 原文实现；未实现的特性（延迟 ACK、SACK、重排序检测）写进设计文档，而不是假装没有 |
| "已有类似项目" | 立项前扫描 mooncakes.io 全部 2491 个包，没有任何项目建模 TCP 的丢包响应行为；与最接近的 moonsim 的逐项对照见 [docs/positioning.md](positioning.md) |
| 单次实验不可信 | 按包身份的受控丢包 + `--seeds` 多种子平均，报告同时给出均值、最快与最慢 |
| 未验证的结论被写进文档 | 每个数字都能用仓库里的命令复算；发现不可信就改文档而不是保留（已经发生过两次） |

## 五、相关研究与实践基础

**标准依据**：RFC 5681、6298、6582、6928、9438，以及队列管理的 RFC 8289（CoDel）。CUBIC 的常数与公式在实现前逐条核对原文；实现方式参考生产实现而非教科书伪代码，例如拥塞避免用"每 N 个 ACK 加一个报文"的计数方式。

**两次自我推翻**：早期宣称"长肥链路上 CUBIC 比 Reno 快 7.9 倍"，那个数字来自不受控的实验——同一种子只保证同样的随机源，链路按发送顺序抽签，两个算法遇到的其实是两串不同的丢包；改成按包身份决定丢包后，单次运行又显示 CUBIC 更慢，加上 `--seeds 3` 才稳定为均值快 3.2 倍、超时次数五分之一（218.6 秒对 706.1 秒，23 次对 112 次）。

**本期的实测结果**：缓冲区从 64 个包加到 600 个包，同一段传输从 7.403 秒变成 16.610 秒、最坏排队延迟从 104.4 毫秒涨到 978.7 毫秒；换成 CoDel 回到 5.044 秒与 226.4 毫秒。同一组实验还跑出 RED 把连接锁死的结果（3 MB 数据 19273.9 秒、326 次超时，换拥塞控制同样复现）。多流实验里 4 条流共用 10 Mbps 链路，聚合 9.75 Mbps（97%），两条 CUBIC 流稳定拿到两条 Reno 流约两倍份额。

**一个尚未解释的异常**：成批丢失之后，连接有时会退化成靠 60 秒定时器推进（小缓冲区下 Reno 传 3 MB 用了 10047 秒、192 次超时，而队列平均占用是 0.0 个包）。只记数据与复现命令，没有粉饰成结论。
