## 一、这是什么

**一句话**：给定链路参数、流量和一个随机种子，输出逐字节一致的事件序列与指标——把"网络在这组参数下会怎样"变成可复现、可比较、可回归的实验。

它**不是**通用仿真框架，也**不是**网络协议栈。它是一台仪器：一端是链路物理（带宽、传播延迟、抖动、按字节限制的队列、队列管理策略），另一端是传输协议行为（TCP 状态机、RTO 估计、拥塞控制）。五个命令行子命令就是全部接口：`run` / `compare` / `sweep` / `list` / `version`。

## 二、给谁用、怎么用

四类下游用户，走同一条命令路径：

**1. 学与教拥塞控制的人**——把公式变成能动手的实验。

```bash
moon run cmd/moonnet -- compare scenarios/long-fat.json --cc reno,cubic --seeds 3
```

不需要装 Mininet、不需要 root、不需要 Linux，在 Windows 和 CI 里都能跑，而且同一场景跑两次结果逐字节相同。

**2. 设计与评估协议和算法的人**——写一个拥塞控制算法就是实现一个 7 方法的接口，然后把新旧算法放进同一个场景对比。库自带 RFC 标准实现（Reno、CUBIC）作为对照基线，所以"我的算法比标准实现好在哪"有可信参照；丢包按包身份决定，两行遇到的是同一串丢包。队列策略同理：`discipline` 在场景文件里，`--discipline` 在命令行上，换策略不需要改代码；"我的算法在 CoDel 下面还成立吗"是一行命令，而不是另一个工程。

**3. 判断链路参数该取什么值的人**——缓冲区开多大、链路上要不要开队列管理、开了会不会伤吞吐，这些是部署问题而不是算法问题。本项目把"同一条路径 + 同一份数据 + 同一个算法，只改一个参数"做成默认的实验形式（`--discipline`、`sweep`、`--seeds`），所以参数变化带来的后果是测出来的，不是引用的。

**4. 将来做 MoonBit 网络栈的人**——把仿真器当回归测试台。MoonBit 目前没有网络协议栈；一旦有人开始写，最先需要的就是能在 `moon test` 里跑的确定性行为验证环境。

## 三、与 moonsim 的关系：研究对象不同，不是功能多少不同

先承认重叠：两者都是 MoonBit 里的确定性仿真，都提供虚拟时间、种子、扫描、多种子矩阵。这一层确实重叠，这正是"已被覆盖"这个判断的来源。

区别在**研究对象**：

| | moonsim | moonnet-lab |
| --- | --- | --- |
| 研究对象 | 服务的可靠性逻辑（消息、任务、状态机、外部调用） | 网络与传输协议的行为 |
| 网络模型 | 抽象消息层：延迟区间 + 丢弃百分比，单位是 tick | 链路：带宽、传播延迟、抖动、按字节限制的队列 |
| 队列 | 排队论模型（顾客、服务时间） | 有界缓冲区 + 队列管理策略（drop-tail / RED / CoDel），排队延迟是可测量的量 |
| 协议 | 无 | TCP 状态机、RFC 6298 的 RTO 估计、快速重传、多丢包恢复 |
| 算法 | 重试、熔断、限流、负载均衡等可靠性模式 | Reno、CUBIC 等拥塞控制 |
| 时间单位 | tick（抽象） | 皮秒（可手算校验：1500 字节 @ 10 Mbps = 1.2 毫秒） |

**判断一个差异是"本质"还是"功能"，标准是它是否改变了能够回答的问题。** moonsim 的模型里没有"拥塞窗口"这个概念，所以下面两组结果它结构上无法产出：

```text
$ moon run cmd/moonnet -- compare scenarios/long-fat.json --cc reno,cubic --seeds 3
reno   mean  706.083s   timeouts 112
cubic  mean  218.618s   timeouts  23

$ moon run cmd/moonnet -- run scenarios/fairness.json
flow 0 reno 31.0% | flow 1 reno 8.7% | flow 2 cubic 30.9% | flow 3 cubic 29.2%
Jain index 0.8754，聚合 9.75 Mbps（10 Mbps 链路的 97%）

$ moon run cmd/moonnet -- run scenarios/bufferbloat.json                 # drop-tail
elapsed 16.610s   throughput 1444.9 kbit/s   worst queueing delay 978.7 ms

$ moon run cmd/moonnet -- run scenarios/bufferbloat.json --discipline codel
elapsed  5.044s   throughput 4757.7 kbit/s   worst queueing delay 226.4 ms

$ moon run cmd/moonnet -- run scenarios/bufferbloat-shallow.json         # 缓冲区 64 包
elapsed  7.403s   throughput 3241.7 kbit/s   worst queueing delay 104.4 ms
```

这不是"更多的功能"，而是"另一种仪器"。第三组数字最说明问题：**同一条 5 Mbps 链路、同一份 3 MB 数据、同一个拥塞控制，只把缓冲区的深度从 64 个包加到 600 个包，传输就慢了 2.2 倍、排队延迟涨了 9.4 倍**；把"满了才丢"换成"队头等待超过 5 毫秒就提前丢"，传输又快回 3.3 倍、排队延迟降到 226 毫秒。这里起作用的是一个回路——缓冲区深度改变排队延迟，排队延迟改变往返时间，往返时间改变拥塞窗口的收敛速度，窗口再决定缓冲区里堆多少。moonsim 的模型里没有拥塞窗口，也没有队头等待时间，这个回路在它的抽象里不存在，所以它结构上产不出这组数字。**这就是"本质区别"的可操作定义：差异改变了能够回答的问题，而不只是多了一个开关。**

同一组实验还跑出一个谁都没预期的结果：RED 在这条路径上把连接锁死了（3 MB 数据 19273.9 秒、326 次超时），因为它的判定量是"到达时更新的平均占用"，单条流停止发包后这个平均值降不下来。这不是我们设计的结论，是实验台上跑出来的，并且换个拥塞控制同样复现（`--cc reno` 为 17128.9 秒）。这条结果的价值不在于 RED 好不好，而在于它证明这台仪器能产出文献之外的新数据。

**为什么不作为补丁贡献给 moonsim**：两个技术原因。其一，时间粒度不兼容——moonsim 的核心单位是 tick，而链路串行化要求整数时间精确到皮秒级，把 tick 替换掉会改变它的核心语义与全部既有结果。其二，范围不同——moonsim 明确声明"专注模型测试；真实网络压测和生产基础设施运行由对应工具负责"，它 0.3.x 的稳定性承诺也不适合容纳一个仍在演进的协议模型。如果维护者认为 `models/tcp` 值得做，那是一条合理的替代路径，但它会是另一个更小的东西：一个模型文件，而不是一台实验台（含场景文件、受控丢包、多流公平性与报告）。

**更要紧的一句**：如果生态只能留一个，应该留 moonsim，把本项目里最有价值的部分——TCP 与拥塞控制的模型——作为它的一个领域模型上游。这也是我们愿意接受的结果。

## 四、与 Mininet、ns-3 的关系

| | Mininet | ns-3 | moonnet-lab |
| --- | --- | --- | --- |
| 原理 | 真实 Linux 内核协议栈 + namespace + tc/netem | 离散事件仿真（C++） | 离散事件仿真（MoonBit） |
| 保真度 | 最高（真实协议栈） | 中 | 中（协议按 RFC 实现） |
| 可复现 | 差（真实时钟与内核调度） | 好 | 好（事件序、随机数、丢包位置全部固定） |
| 运行环境 | Linux + root，或虚拟机/容器 | 独立工程 | 任意平台，可嵌入 `moon test` 与 CI |
| 换算法 | 需要写内核模块 | 需要改 C++ 并重编 | 实现一个 7 方法的接口 |

Mininet 是保真度最高的选择：如果目标是"验证真实协议栈在真实硬件上的行为"，没有理由重做它。但它的三个性质决定了它承担不了本项目的用途：不可复现、需要 root 与 Linux、无法嵌入一个语言的测试套件。**本项目的定位是"语言生态内可嵌入、可复现的实验台"，不是 Mininet 的替代品**——就像 ns-3 也没有替代 Mininet，两者服务不同的问题。

## 五、MVP 的范围

仓库只做一件事的两端：链路物理与传输协议行为，以及跑实验的最小装置。

**保留**（够用的最小集合）：

- `src/sim` 确定性事件内核：虚拟时间、事件序、冻结的随机源
- `src/net` 数据包、队列（drop-tail / RED / CoDel）、链路（带宽 / 延迟 / 抖动 / 丢包）
- `src/tcp` TCP 状态机、RFC 6298 重传、快速重传与多丢包恢复、Reno、CUBIC
- `src/lab` 场景文件、运行、报告、对比与扫描、多流公平性
- `cmd/moonnet` 五个子命令
- `scenarios/` 示例场景（长肥链路、多流公平性、小缓冲、干净局域网、缓冲区膨胀深浅两版）

**明确不做**：通用仿真框架（用 moonsim）、pcap 解析（已有实现）、与真实网络互操作（用 Mininet）、大规模并发、图形界面。

## 六、诚实的局限

- **领域深、覆盖面窄**：只做网络这一块；其他领域请用 moonsim。本项目也不打算扩展到通用仿真。
- **模型不是真实协议栈**：延迟、丢包、队列都是模型。凡"真实内核在真实硬件上会怎样"的问题，应该用 Mininet。
- **尚未实现的标准特性**：延迟 ACK、SACK、重排序检测等，写在设计文档的"已知边界"里，而不是假装没有。
- **两个未解决的待查问题**，都来自成批丢失之后的恢复：一是某次采样中 CUBIC 的平均窗口是 Reno 的七倍却完成得更慢，最可能是丢失的 ACK 只能靠超时补救；二是小缓冲区下 Reno 会退化成"每 60 秒推进一次"（3 MB 数据 10047 秒、192 次超时），而队列平均占用是 0.0 个包——连接不是被路径拖住的，是自己停住的。两条都标在路线图里，只记数据和复现命令，没有粉饰成结论。也正因为第二条没查清，README 里的缓冲区对比把算法固定在 CUBIC 上。

## 七、项目的意义

1. **生态空白**：立项前扫描 mooncakes.io 全部 2491 个包，拥塞控制、丢包恢复相关关键词的命中都是同名误匹配。生态里有链接库、有协议头解析，但没有可以验证协议**行为**的环境。
2. **可复现本身是基础设施**：它不是产品，而是让别人（以及 AI 代理）能对协议做实验的地基——确定性加上机器可读报告，意味着实验可以被复算、被推翻、被固化进回归测试。
3. **教学价值**：TCP 拥塞控制是最经典也最难讲清的主题之一。把它变成能跑的代码、能改的参数、能对比的两种算法，是这个项目最直接的用途。

## 八、验证方式

- **95 个测试**：时间换算、事件排序、随机数参考向量、队列丢弃与三种队列管理策略（谁会在缓冲区未满时丢、谁会提前丢、CoDel 的控制律何时动手）、链路串行化、握手与状态机、窗口与在途字节、乱序重组、RTO 估计、Karn 算法、快速重传与多丢包恢复、两种拥塞控制的窗口演化、JSON 读写、场景解析与错误消息、公平性指数端点、聚合吞吐不超过链路容量，以及"同一个场景只换队列策略，排队延迟减半"的端到端断言。
- **物理量检查**：聚合吞吐不得超过"带宽 × 时间窗"。这条断言在开发中抓出过一次真实错误：窗口到期后仍排空事件队列，让 20 MB 数据"在 5 秒内"通过了 10 Mbps 链路。
- **确定性检查**：随机数参考向量钉死；"同一场景跑两遍逐字节一致"作为断言；丢包按包身份固定。
- **CI**：在干净的 Linux runner 上执行测试、场景文件与对比命令。
