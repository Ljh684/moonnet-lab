## 目标

调拥塞控制、评估缓冲区该多大、判断丢包时该用哪个算法——这些问题的答案通常来自真实设备上的试错，或者来自一次无法复现的临时脚本。两者都有同一个毛病：换一台机器、换一次运行，数字就变了，结论既无法比较也无法积累。

moonnet-lab 把网络行为建模成纯函数：给定场景文件与随机种子，任意多次运行都产出逐字节一致的事件序列与指标。于是算法对比、参数扫描和结论回归都能像代码一样被复现和版本化。适用场景是网络工程师的参数决策、拥塞控制的教学与研究，以及为 MoonBit 生态提供可复现的协议行为验证台。

## 交付物

- **确定性内核**：皮秒整数虚拟时间、按 `(时间, 调度序号)` 排序的事件队列、参考向量钉死的随机源
- **网络层**：数据包与身份标签、有界队列（drop-tail）、链路（带宽 / 延迟 / 抖动 / 丢包）
- **TCP 协议栈**：状态机、滑动窗口、乱序重组、RFC 6298 的 RTO 估计、Karn 算法、超时重传与指数退避、快速重传与多丢包恢复
- **拥塞控制**：可插拔接口 + Reno（RFC 5681 / 6928）与 CUBIC（RFC 9438，含 Reno 友好区）
- **实验设施**：4 个可编辑场景文件、固定字段顺序的 JSON 报告、`compare` / `sweep` 对比与扫描、`--seeds` 多种子平均
- **质量**：83 个测试全部通过；CI 在干净的 Linux 环境执行测试、演示与场景工具

边界：不做通用离散事件框架、不解析 pcap、不与真实网络协议栈互操作。

## 技术路线

**分层严格**：`sim` 不认识网络，`net` 不认识 TCP，`tcp` 不认识文件；数据包是 `Packet[T]`，协议状态由上层挂在包里；库接受字符串，只有命令行工具碰文件系统。

**机制与策略分离**：拥塞控制是一个接口，只回答"现在允许多少字节在途"以及六种事件下窗口怎么变。换一个算法不需要改任何一行机制代码。

**三个确定性支柱**：时间是 `Int64` 皮秒，没有浮点调度决策；事件顺序由 `(时间, 调度序号)` 唯一确定；随机数算法冻结在包内并有参考向量。

**AI 工具的分工**：AI 承担实现、测试与文档；算法保真度、实验设计，以及"哪些数字不可信"由我把关——CUBIC 的常数逐条对照 RFC 原文，可疑结论必须能独立复算。

## 独立完成的验证工作

开发过程中项目两次推翻了自己的结论：

1. 早期宣称"长肥链路上 CUBIC 比 Reno 快 7.9 倍"。这个数字来自不受控的实验：链路按发送顺序抽签，两个算法遇到的其实是两串不同的丢包。改成**按包身份决定丢包**后，两行遇到同一串丢失的数据。
2. 受控之后，单次运行显示 CUBIC 更慢；加上多种子平均后反转为**均值下快 3.2 倍、超时 23 次对 112 次**。因为丢包场景的总时间由少数几次 60 秒封顶的超时主导，一次运行不是一个测量。

仍有一个未解决的待查问题写在路线图里而不是粉饰成结论：某次采样中 CUBIC 的平均窗口是 Reno 的七倍却耗时更长，说明连接在反复停顿，最可能的原因是丢失的 ACK 只能靠超时补救。
